# Memory & knowledge vault

This chapter covers what Claude keeps between sessions: its own memory (an index plus one fact per file) and an external technical knowledge vault (map, module notes, concepts, IMPACT playbooks, audits). Claude reads the vault before changing code and updates it after each sprint, or right after a multi-sprint program (MEM-025).
To reuse it, fill in the `<PLACEHOLDERS>` (memory directory, vault path, durable program folder `<PROGRAM_DIR>`, deployment doc, runbook, and the personal-vault status note if the user keeps one), then create the vault skeleton and the first module notes before the first feature sprint.

## Memory structure

- **MEM-001** `MUST` Organize memory as one index file (`<MEMORY_DIR>/MEMORY.md`) plus one topic per file. Each index line holds a link and a one-line hook: absolute dates, status flags (`LIVE` / `DEPLOYED` / `NOT DEPLOYED` / `UNCOMMITTED`), commit hashes and the key gotcha. — _why:_ the index shows the state of the project at a glance without opening any file.
- **MEM-002** `MUST` Give every memory file frontmatter with `name`, `description` (one line that lets a future session judge relevance without opening the file; for delivery memories, include the outcome and the deploy status) and `type` (`project` | `feedback` | `reference`). Write the body as the fact, followed by a **Why:** section and a **How to apply:** section. Cross-link related memories with `[[wiki-links]]`.
- **MEM-003** `MUST` Use absolute dates (YYYY-MM-DD), never relative ones, and update an existing memory in place with dated `UPDATE <date>:` lines instead of creating a duplicate.
- **MEM-029** `SHOULD` Append follow-up fixes and small follow-up rounds on the same feature to its existing memory as dated sections. Start a new file only for a new delivery round or program, and link it to the previous one with `[[wiki-links]]`.
- **MEM-004** `MUST` When a decision is superseded, mark the old memory as historical and link it to its replacement. When an item is resolved, mark it inline with the date (`[RESOLVED <date>]`) instead of deleting it.
- **MEM-030** `MUST NOT` Never write passwords, tokens, keys or other secrets (including local demo or test passwords) into memory files, the memory index or vault notes. Name the place they live instead (for example "the `DEMO_PASSWORD` variable in the backend `.env`"). — _why:_ memory and vault are plaintext files that persist across sessions and get copied into agent prompts (SEC-064, SEC-074).

## Delivery and program memories

- **MEM-005** `SHOULD` Structure every delivery or program memory (audits, multi-sprint plans) in this order: (1) absolute dates and current state; (2) commit hashes, test counts, and deploy status with the deployment id, or `NOT DEPLOYED` with the reason; (3) where the results live (MEM-010); (4) "What to know next time" (MEM-008); (5) open decisions, next steps and what you are waiting on from the PO (the "Remaining" list of DEL-011); then the **Why:** and **How to apply:** sections from MEM-002.
- **MEM-008** `SHOULD` Give each feature-area memory a "What to know next time" section. It says where the data actually lives (for example inside an opaque JSON draft rather than its own table), which stored values are client-supplied and must therefore be clamped or validated server-side when read, and which verification path works when the obvious one fails (for example a dev-only route checked through JS when screenshots crash).
- **MEM-009** `SHOULD` Record an incident in memory right away. Include its impact, verified read-only, and the rule that prevents a repeat (for example, an explicit ban on a dangerous command in agent prompts).
- **MEM-010** `MUST` Save large audit, workflow and program outputs in `<PROGRAM_DIR>/<program-id>/` or on an artifact page, never only in the session scratchpad. Include the workflow scripts, the approved plan JSON, the per-sprint plans, the sprint reports, the open items, a program summary and the `HANDOFF.md` from DEL-042. The memory entry links that folder, and any remaining pointer to a session-scratchpad file is labelled "may be deleted". — _why:_ scratchpad files can disappear.

## Gotchas

- **MEM-011** `MUST` Save each root-cause bug as a "do not reintroduce" gotcha. Give it a concrete check to run before deep-debugging similar code, such as a new fetch wrapper or form. — _why:_ it saves re-diagnosis; two such bugs once blocked an entire core user flow.
- **MEM-012** `SHOULD` Record every tooling gotcha together with the workaround that works. Cross-link (`[[note-name]]`) earlier notes that share the same root cause. — _why:_ several environment traps share one root cause (for example, `requestAnimationFrame` paused in a hidden preview pane), and the link saves rediscovering it.
- **MEM-013** `SHOULD` After any infrastructure change (new service, slot, region or domain), update the deploy memory note in the same pass as `<DEPLOYMENT_DOC>` and `<RUNBOOK>` (SOT-045; the deployment doc's dated current-state banner and the promotion records: OPS-102). Record the new service names and ids, URLs, region and which slot or instance is currently active, and mark the old values as historical. Keep platform gotchas only in the deployment doc's "do not rediscover" list, so this operational knowledge lives in the repo and not only in memory; the memory note links to it and does not copy it.

## Knowledge vault layout

- **MEM-014** `MUST` Keep a technical knowledge vault at `<VAULT_PATH>` as plain Markdown notes with wiki-links (Obsidian-compatible), in numbered folders: `00 Map`, `10 Backend modules`, `20 Frontend`, `30 Shared`, `40 Concepts`, `50 Impact playbooks`, `60 Audits`. `00 Map` holds the entry map note, one end-to-end flow note per user role, a data-model note, an architecture-and-deploy note and "Observations and limits". The vault may live outside the repo; if it does, every agent preamble gives its absolute path. — _why:_ it is the dependency map that Claude and the PO read before touching code.
- **MEM-015** `MUST` Write one note per real code module, on a fixed template: Role, Key files, Exposes, Depends on, Used by, Tables touched, Events, "If you change this, check" and Known pitfalls.
- **MEM-016** `MUST` Give every vault note frontmatter (`type: module|concept|impact|map|audit`, `zone`, `updated: YYYY-MM-DD`) and a first line `Updated <date>: <what changed>`. Add later changes as dated sections titled with the work-package id. Never rewrite a note silently.
- **MEM-017** `SHOULD` Refer to code by file name, which stays stable. Treat any cited line number as valid only on the date it was written. — _why:_ line numbers drift with later edits.
- **MEM-018** `SHOULD` Put one "value chain" diagram in the map note. It traces a request from the browser through the gateway, guards, services and DB, then on to the side effects in the same transaction, the workers and the external services.
- **MEM-019** `SHOULD` Keep cross-cutting concept notes, linked from the map, one per cross-cutting concern of your system, for example money, state machines, events/notifications, deadlines/jobs, authorization, idempotency, uploads and i18n. End each concept note with a link to its full procedure in an IMPACT note.
- **MEM-020** `SHOULD` Write each IMPACT playbook as an ordered, numbered checklist, one per risky change type in your system, for example schema change, new endpoint, status enum, new event, UI text, money flow, env and deploy. Link it to the relevant concept and module notes, name a past change as the "model to follow", and point to the repo skill that encodes the same procedure.
- **MEM-021** `SHOULD` Document couplings that are tighter than the module import graph shows. Examples are file-level imports across modules, a guard that reads another domain's tables, and one sweep job that re-arms other modules' deadlines. — _why:_ otherwise whoever changes one side misses the hidden dependent.
- **MEM-022** `MUST` Keep an "Observations and limits" note in the map. It records how the vault was built or refreshed (date, source snapshot, method) and what was not verified (for example no tests run and no production checks, with test counts and production state copied from CHANGELOG/docs rather than observed), what has been fixed since and what is still open. Mark older audit annexes as historical, not as the current state. — _why:_ an annex written before a fix sprint describes bugs that are already fixed.
- **MEM-023** `MUST NOT` Never write technical notes into the user's (PO's) personal second-brain vault; it belongs to them. The only permitted edit there is the project-status note at `<PERSONAL_VAULT_STATUS_NOTE>`, and only when the project's state changes (a sprint delivered, a decision made).

## Reading the vault before a change

- **MEM-024** `MUST` Before editing code, open the map note. Then read each affected module note in full (at minimum "If you change this, check" and "Known pitfalls") and the IMPACT playbook that matches the change type. Read the `.md` files directly; the Obsidian app is not needed. When you delegate, put `<VAULT_PATH>` (on Windows, in both native and POSIX form) and this instruction, with the names of the matching playbooks, in every subagent's shared preamble (DEL-035).

## Updating the vault after a sprint

- **MEM-025** `MUST` After every sprint that changes architecture, flows, enums or dependencies, do one of two things. (a) Update the affected vault notes now: at least "If you change this, check" and "Known pitfalls", plus a dated line in "Observations and limits". (b) Inside a multi-sprint automated program: list the affected notes in that sprint's CHANGELOG entry and add an unchecked "refresh vault notes: <list>" item to the acceptance checklist, then refresh every listed note as the post-program step in DEL-042, before anyone relies on the vault. Tell the PO when the vault has been updated. — _why:_ an outdated vault is worse than none, because it states wrong things with authority.
- **MEM-027** `MUST` Treat the vault as stale when the CHANGELOG or git log shows sprints that touched modules after the latest dated entry in "Observations and limits" with no recorded refresh. Then refresh the whole vault in one pass before relying on it. Run parallel read-only subagents, one per group of related notes, plus one agent that rewrites the map notes from their reports. They read the working tree, CHANGELOG.md and the implementation docs. Spot-check the code wherever reports contradict each other. Give each touched note its dated "Updated" line, collect the open questions the agents raise into the triage backlog, and save the refresh script in `<PROGRAM_DIR>` for reuse (MEM-010). — _why:_ a vault left untouched for a month while the app changed heavily no longer matched the code.
- **MEM-028** `MUST` Build and refresh vault notes, audits and other generated documentation from the working tree on disk, never from HEAD, and say so in the note (as its source snapshot, MEM-022). — _why:_ with many sprints stacked uncommitted, HEAD can lag far behind the code that exists and may already be deployed.

## Adapting to a new project

- Set `<MEMORY_DIR>` (Claude's per-project memory folder) and create `MEMORY.md` with the index line format from MEM-001 and the status flags you will use.
- Choose `<VAULT_PATH>`, inside or outside the repo (if outside, every agent preamble carries its absolute path, MEM-014, MEM-024). Create the numbered folders from MEM-014, and drop or rename zones your stack lacks (for example, `30 Shared` if there is no shared package).
- Write the module-note template (MEM-015) and the frontmatter schema (MEM-016) once, as files in the vault, then write one note per real module.
- Pick the concept notes (MEM-019) and IMPACT playbooks (MEM-020) for your system's cross-cutting concerns and risky change types, and link each playbook to the matching repo skill.
- Create the map note with the value-chain diagram (MEM-018) and an empty "Observations and limits" note (MEM-022).
- Decide `<PROGRAM_DIR>`, the durable home for audit, workflow and program outputs (MEM-010), along with `<DEPLOYMENT_DOC>` and `<RUNBOOK>` for infrastructure state and deploy gotchas (MEM-013).
- Decide where secrets live (env files, secret manager) so memory and vault notes name the location, never the value (MEM-030).
- If the user keeps a personal vault, record its path and the single project-status note Claude may update (`<PERSONAL_VAULT_STATUS_NOTE>`, MEM-023).
- Add a step to the sprint-closing checklist: "vault notes refreshed, or listed as an unchecked refresh item for the post-program step" (MEM-025).
