# Release & operations

This chapter covers everything between a green commit and a healthy production: consent before outward actions, container images, config and secrets, migrations, release identity, blue/green promotion and rollback, health checks, production data operations, backups, region placement, email and domain, and platform/CLI gotchas.
The rules assume a pnpm monorepo (NestJS + Prisma + PostgreSQL + Redis/BullMQ + S3-compatible storage, Next.js frontend) shipped as Docker images to a PaaS such as Railway. On another platform, keep each rule's intent and map the mechanism (`railway run` → your platform's "run with service env" command). Fill in the `<PLACEHOLDERS>` once and record them in the project's `CLAUDE.md` and `<DEPLOYMENT_DOC>`.

## Consent and outward actions

- **OPS-001** `MUST` Deploy, push, run production migrations or promote a release only with explicit approval from the user or product owner, given in the current session. Approval for one deploy does not cover the next. If approval is missing, mark the work NOT DEPLOYED and record the exact command still to run (general rule: WM-021; status label: PO-009). — _why:_ an automated permission check can ask for fresh consent even right after an earlier approved deploy.
- **OPS-002** `MUST NOT` Treat a rollout, acceptance or runbook document as authorization to deploy. Offer a checkpoint commit command for review instead of executing it.
- **OPS-003** `MUST` List the production steps in a "Prod steps (after approval)" section, in execution order, and run none of them before that approval.
- **OPS-004** `SHOULD` Keep git commit/push and deploy CLIs out of the permission allowlist, so every outward-facing action still asks for explicit confirmation.
- **OPS-005** `MUST` Every subagent/implementer prompt carries an explicit prohibition, whatever the task: "do not run `<DEPLOY_CLI>`, git commit/push, or any deploy, migration-on-production or other outward command." Never put a runnable deploy command inside a prompt, even quoted as an example. — _why:_ a deploy command quoted in backticks inside a prompt string was once executed by an implementer agent.
- **OPS-006** `MUST` After any accidental outward action, first verify its impact read-only (for example, list deployments), then report it to the user at once as an INCIDENT with target, time, observed effect and how to undo it, and record it in memory (MEM-009).
- **OPS-007** `MUST` When cutting a release checkpoint, preserve the existing working tree and index, and push nothing that was not approved.
- **OPS-008** `MUST NOT` Delete cloud projects or services yourself. Report stray resources, such as a project created by mistake, to the owner for deletion.
- **OPS-101** `GOTCHA` Never leave the main development checkout linked to a production service. Link only dedicated release worktrees, and run `<PLATFORM_CLI> status` to confirm the linked service before any platform command. — _why:_ the main checkout was linked to a service in the production environment, so a deploy command an implementer ran by accident started a real deployment there.

## Migrations during development

- **OPS-010** `MUST` During development, apply migrations only to local or isolated databases. Production gets nothing until an authorized deploy.

## Container images

- **OPS-011** `MUST` Pin every base image and tool image (runtime, gateway, image scanner, storage/CLI helpers) by digest (`image@sha256:...`) in every stage, prefer official images, and bump digests deliberately. — _why:_ reproducible builds and controlled intake of upstream changes and CVEs.
- **OPS-012** `MUST` Build the production image from the monorepo root in three stages. **build**: frozen-lockfile install, build the shared package first, generate the ORM client, build the backend, assert `dist/main.js` exists, build the frontend. **prod-deps**: `pnpm install --frozen-lockfile --prod --filter <backend>...` plus client generation. **runtime**: copy `node_modules` only from prod-deps and `dist/` only from build. — _why:_ no dev dependencies or sources ship in the runtime image.
- **OPS-013** `SHOULD` End the runtime stage with one network-free self-check `RUN` step, executed at build time: it asserts the entrypoint, the build outputs and the migration files (including the migration lock file) are present, resolves the critical runtime dependencies (including the ORM CLI, and a generated client that contains an expected model), and fails if any dev tool (test runner, bundler, compiler, lint plugin, framework CLI) is among the installed packages. A leaked dev tool or a runtime dependency missing from `dependencies` then fails the build. Upgrade OS packages, ship no global npm/npx/corepack, and rebuild without cache if the image scan reports a stale apt layer.
- **OPS-014** `GOTCHA` A `--prod` install (prod-deps stage, `pnpm deploy --prod`) drops devDependencies. Before switching to it, move every tool the runtime calls into `dependencies`, for example the Prisma CLI used by boot migrations (STK-118), and let the OPS-013 self-check prove it.
- **OPS-015** `MUST` Run as a non-root user (`USER node`), copy only runtime artifacts, and keep local demo defaults strictly separate from deployment secrets.
- **OPS-016** `MUST` The container entrypoint either `exec`s node or traps SIGTERM/SIGINT and forwards them to every child process before waiting on them. It validates its mode variables and exits non-zero on invalid values, and it exits non-zero as soon as any child dies (`wait -n`) so the platform restarts the container. — _why:_ a bash PID 1 without exec or trap cut off the ORM, queue-worker and headless-browser shutdown hooks in production; `set -e` does not apply to `wait`.
- **OPS-017** `GOTCHA` On Debian slim (bookworm) images, install `openssl` before `pnpm install` and `prisma generate`, in every stage that generates the Prisma client. — _why:_ otherwise Prisma cannot detect the platform's OpenSSL, picks the openssl-1.1.x engine and the container crashes at runtime.
- **OPS-018** `GOTCHA` For a Next.js standalone image: pin pnpm with corepack, install with `--frozen-lockfile` filtered to the app and the shared package, build shared before the app, run `server.js` from its monorepo sub-path, and `mkdir -p public` before building. Whenever you create a directory the app needs at runtime, confirm the production Dockerfile copies it. — _why:_ `public/` is optional in Next, but the final stage's COPY fails if it is missing.
- **OPS-019** `GOTCHA` `NEXT_PUBLIC_*` values are baked into the bundle at build time. Declare each as `ARG` + `ENV` in every Dockerfile with a valid default (a valid `http://localhost` URL for the site URL, never empty), rebuild every deployment (not just restart) when a value changes, build with the canonical production URL rather than a slot URL, and never put anything sensitive in one. Document each in `.env.example`: what it does, that it is baked, and that empty disables the integration. — _why:_ an empty site URL once broke the build, and a wrong one makes production send `X-Robots-Tag: noindex` (check after each deploy, OPS-059).
- **OPS-020** `SHOULD` When the platform limits the service count, ship frontend and backend in one container: the backend binds only to `127.0.0.1` (`LISTEN_HOST`) and the Next.js server proxies the API and websocket paths to it through a loopback rewrite. — _why:_ the browser sees a single origin (SameSite=Lax cookies keep working, no CORS, no third-party cookies) and the backend is unreachable from the private network.
- **OPS-021** `MUST` Init scripts read credentials from quoted environment variables instead of interpolating secrets into shell code. Percent-encode special characters in `DATABASE_URL` passwords.
- **OPS-022** `SHOULD` In CI, confirm the image contains its expected build outputs (standalone server, static dir, backend dist entry) with `docker run --rm --entrypoint sh <image> -c 'test -f ... && test -d ...'`.
- **OPS-023** `SHOULD` Validate the production compose file with `docker compose config --quiet`. It must fail when required secrets are removed and pass with synthetic values supplied only to the child process. Never start the stack for this check.
- **OPS-024** `MUST` Smoke-test the production container with a harness that refuses to reuse an existing project and generates ephemeral secrets in memory. It isolates dependencies on a new network, binds only `127.0.0.1`, checks pages, static assets, health and a real write confirmed by direct SQL, then removes only its own containers, network and volumes. Its report holds no secrets or PII.

## Configuration and secrets

- **OPS-025** `MUST` Keep secrets only as platform service variables, with the platform dashboard as the source of truth.
- **OPS-026** `MUST` Set every newly required env var or rotated key on ALL deployment slots before deploying the release that needs it. Generate it (e.g. `openssl rand -hex 32`), set it with `<PLATFORM_CLI> variables --set ... --service <svc> --skip-deploys`, then redeploy in coordination: standby first, verify, then active. Make sure the old release still boots with the variable present or absent. — _why:_ boot-time config validation aborts a slot that is missing it, a new code path can silently degrade without it (e.g. data stays unencrypted), and setting a variable without `--skip-deploys` triggers an extra redeploy.
- **OPS-027** `MUST` Operations that take money fail closed with 503 `<NOT_CONFIGURED_CODE>` while required seller/legal settings are missing, invalid or still placeholder seed values; upstream provider failures return 502. Optional integrations (error tracker, analytics, trusted client-IP header, payment provider) are disabled while their env var is empty, so every release boots with or without them (OPS-026); a disabled money-taking integration answers 503 and falls back to the manual path (UI fallback: ENG-116).
- **OPS-028** `MUST` Keep platform deploy settings as config-as-code (health check path, ~300 s startup timeout, zero overlap, ~60 s drain, restart ON_FAILURE with capped retries) and confirm them in the live service metadata before the first traffic switch. — _why:_ CLI-created services did not expose the declared values; repository config alone is not live evidence.
- **OPS-029** `SHOULD` Make boot-time dependency checks (SMTP verify, Redis subscriptions) non-blocking, with a single warning per error episode. — _why:_ a dependency that is down at boot must not take the site down.

## Release identity and CI gate

- **OPS-030** `MUST` Identify every release by an immutable annotated tag (`<RELEASE_TAG_PATTERN>`, e.g. `release/YYYY-MM-DD-<name>`) on the full Git SHA, built from a clean dedicated release branch/worktree with a commit and a CHANGELOG entry, never from the live working tree. A build that reports `sha=unknown` must not be promoted. When a retained image's source SHA is unknown, use its image digest as the identity and never invent a SHA. — _why:_ a deploy from a dirty tree reports an unknown release SHA and cannot be promoted.
- **OPS-031** `MUST` Before every deploy, run the exact-SHA CI gate script: the commit's CI run must be green on that exact 40-hex SHA; a push to main, a release tag or a manual dispatch counts, a green PR run does not, and a short SHA is refused. The pre-deploy security review of the release diff must also be clean (SEC-118). CI concurrency may cancel in-progress runs per ref, but never release-tag runs. — _why:_ release-tag runs are the deploy evidence.

## Migrations

- **OPS-033** `MUST` Make schema changes expand/contract: migrations are additive (new nullable columns, defaults) and compatible with the previous release. Ship DROP, RENAME and destructive cleanup in a separate later contract release, once no deployment slot still runs the old image. — _why:_ with blue/green, the standby (rollback) slot and the active slot read the same database.
- **OPS-034** `MUST` Every migration carries a rollback note in its commit message and a `-- Rollback:` comment in `migration.sql` with the steps in order: stop workers and redeploy the previous app first, archive pending intents, then drop. Never drop a table or column that still holds undelivered work.
- **OPS-035** `MUST` Name migration folders `YYYYMMDDHHMMSS_snake_case_description`. Each hand-written SQL migration starts with a header giving the motivating ID, a pre-verification query that must return 0 rows, and the rollback note.
- **OPS-036** `MUST` Before adding unique indexes or validating constraints in production, run the duplicate pre-check queries from the migration header; every one must return 0.
- **OPS-037** `SHOULD` Introduce a CHECK constraint on a populated production table across two releases: `NOT VALID` first, then `VALIDATE CONSTRAINT` in a later migration, after a query confirms zero violating rows on production and a backup is taken. — _why:_ boot-time migrations must not fail on legacy rows.
- **OPS-038** `MUST` Reference-data defaults (ENG-110) go in through migrations with `INSERT ... ON CONFLICT (key) DO NOTHING` and through seeds with an upsert using `update: {}` (QA-080), so re-running either on production inserts 0 rows and never overwrites admin edits.
- **OPS-039** `MUST` In a single-slot setup, apply migrations at container boot with the idempotent `prisma migrate deploy` before starting the app (`prisma migrate deploy && node dist/main.js`), gated by `RUN_MIGRATIONS=true|false`. Take a backup first, keep a rollback plan and a platform health-check path, and order the rollout so older clients cannot corrupt new-format data. Seeds are never part of boot.
- **OPS-040** `MUST` Run any seed, backfill or one-off script that touches new columns only after that release's migrations are applied to the target database: by the deploy itself when migrations run at boot (OPS-039), or by the explicit migration step in blue/green (OPS-041). Check with `prisma migrate status` first.
- **OPS-041** `MUST` In blue/green production, keep `RUN_MIGRATIONS=false` on both slots after bootstrap; the standby slot refuses to start with it on. Apply reviewed migrations as an explicit, serialized release step, once, before the app, after a backup (dump + SHA-256) and a rehearsal against a restored copy of production.
- **OPS-042** `MUST` Before any schema, auth/session, or event/notification delivery (outbox, queues, email) change, write a contract covering existing-data handling, version compatibility, already-issued tokens and rollback, and rehearse recovery on isolated fixtures before touching user data.
- **OPS-043** `MUST NOT` Replay historical rows as new events when introducing an event/outbox mechanism.

## Blue/green topology

- **OPS-044** `SHOULD` Run two application slots (`<SLOT_A>`/`<SLOT_B>`) built from the same repository and sharing one database, cache/queue and object store, behind a small reverse-proxy gateway (e.g. Caddy `reverse_proxy {$ACTIVE_UPSTREAM}`) that owns the public hostname and routes HTTP and WebSocket traffic to the slot named in a single variable. The previous release stays deployed in standby as the compatible rollback target. — _why:_ hostname, cookies, payment webhooks and callback URLs stay stable while a candidate is tested independently.
- **OPS-045** `MUST` Exactly one slot runs `DEPLOYMENT_MODE=active`. The standby slot fails closed: it registers no queue processors or recurring schedulers, cannot run startup migrations, and a global guard rejects POST/PUT/PATCH/DELETE with 503 and `<STANDBY_ERROR_CODE>` in the canonical error envelope. GET/HEAD/OPTIONS and health remain available. — _why:_ candidate previews cannot mutate production or consume production jobs.
- **OPS-046** `MUST` Register every worker and scheduler through one active-only registration helper, and add each module to a spec that asserts standby registers none. — _why:_ otherwise both slots run workers on the same queues, giving two worker generations.
- **OPS-047** `MUST NOT` Start a second copy of the application container against production dependencies without standby mode. — _why:_ it would immediately run migrations, register schedules and consume the same queues; incompatible worker generations must never overlap.
- **OPS-048** `GOTCHA` The standby guard has no route exceptions, so webhooks (also POST) get 503 there. Keep webhook processing routed to the active slot.
- **OPS-049** `MUST` During a rollout an old client bundle may still be open. Endpoints that take a client-shown version (expected-version check, ENG-009) answer its mismatch with 409 `<STALE_CLIENT_ERROR_CODE>`, write nothing, and the UI reloads the page.
- **OPS-050** `AVOID` Using two complete projects with separate databases as alternating production systems; keep that topology for staging only. — _why:_ independent databases diverge as soon as users write, and cross-project access to one database loses private-network isolation.
- **OPS-051** `GOTCHA` Plan platform capacity before adding services: free plans cap the service count, and blue/green needs two extra services (a second slot and a gateway).

## Promotion

- **OPS-052** `MUST` Once the gates of OPS-031 and SEC-118 pass, deploy a candidate first to the inactive slot in standby, with `RUN_MIGRATIONS=false`, its slot id and its `RELEASE_SHA`. Then run a slot-verification tool that fails on the wrong slot, mode or SHA and checks the localized entry pages and the refusal of mutations.
- **OPS-053** `MUST` Treat the production standby as a read-only preview. Run every write journey (mutations, payments, email, migration rehearsals) in an isolated staging environment with its own data, captured email, separate auth secrets and payments unconfigured; production secrets never go there (SEC-072). Never point the public gateway at an isolated preview, and never transfer preview data into production.
- **OPS-054** `MUST` Before promoting, record a checkpoint: deployment IDs, image digests, SHAs, a variable snapshot, the migration list, queue/outbox and pending-work counts (no PII), and a fresh backup taken through the scheduled backup job (not a manual dump on a PC) and confirmed restorable into a separate database.
- **OPS-102** `MUST` Keep a dated promotion record for every production release. It starts from the OPS-054 checkpoint, naming the identities in full (active/standby slot, deployment IDs, release SHA), and adds the migration and restore evidence, the test results and the exact rollback steps. It ends with a security close (secret handling, fail-closed checks, auth and ownership checks, the SEC-118 result, and a statement that no real customer data was modified) and an explicit `DECISION NEEDED:` line, even when it is "none". Keep runbooks, migration plans and promotion records in the repo (e.g. under `docs/implementation/`); a record grows by appending `Update <date>` sections. After every switch, update the dated "current state" banner at the top of `<DEPLOYMENT_DOC>` and label older addresses and checks as historical. — _why:_ the repo, not memory or chat, must tell the next session which release is live, what it was checked against and how to undo it.
- **OPS-055** `MUST` Classify rollback compatibility for every release. Any change to schema, workers/queues, auth/session semantics, idempotency, provider side effects or persisted JSON formats needs a backward-reader test proving the previous release can read everything the candidate may write. If it cannot, keep the candidate active and fix forward. — _why:_ an older binary is not automatically safe after the new version has accepted writes.
- **OPS-056** `MUST` Promote in this order: (1) old active slot to standby, waiting until its instance stops, workers drain and blocking queue connections reach zero (reads continue, writes get a temporary 503); (2) candidate to active, confirming exactly one worker generation and no duplicate notifications; (3) switch the gateway upstream; (4) verify the public release identity; (5) smoke-test. — _why:_ a short write-only pause prevents incompatible worker generations from overlapping.
- **OPS-057** `MUST` Deploy backend and frontend together and restart all workers; never run old and new mutation workers side by side. Keep documented compatibility windows (e.g. a token-refresh grace period), and test an old session plus a fresh login before rollout. — _why:_ old code does not write the new durable intents.
- **OPS-058** `MUST` After a switch, verify on the public domain that health reports `mode=active`, the expected slot and SHA, and database, cache and storage up. — _why:_ gateway health does not check the mode, so an upstream pointed at a standby slot passes health while every write returns 503.
- **OPS-059** `MUST` After every production deploy, smoke-test: health dependencies, static assets, login/refresh/logout, websocket, a disposable write and delete, an upload and private-file access, a generated document, each primary user journey of every role end to end, including the email each step should send, and an ownership denial. Use one dedicated synthetic account per role: the upload must pass scanning and download byte-for-byte equal, the smoke publishes nothing and notifies no real users, and afterwards you disable the accounts, revoke their tokens, delete the synthetic objects and keep the smoke report. Confirm affected routes return 200, the live HTML carries markers of the new UI, and the canonical host sends no `X-Robots-Tag: noindex` (SEC-092); if it does, the image was built with the wrong site URL, so rebuild it (OPS-019). Then inspect the event/outbox backlog, failed queues, payment checkpoints, pending scans and logs (migrations applied, no missing-config warnings), and record the deployment ID.
- **OPS-060** `MUST` Before enabling live payments, verify checkout resume, late provider responses and signed webhooks in the payment provider's test mode, and confirm the seller/legal settings are real (no placeholder values, OPS-027).
- **OPS-061** `SHOULD` Deploy framework major upgrades (backend framework, HTTP server) to the standby slot first.

## Rollback

- **OPS-062** `MUST` Prefer rolling forward with a fix. To roll back, run the mirror procedure: stop new mutations, move the current slot to standby and drain it, verify pending work is preserved (payment attempts, outbox leases, notification jobs, upload scans), move the previous slot to active with one worker generation, switch the gateway back, and keep the failed slot in standby for investigation.
- **OPS-063** `MUST NOT` Restore the database as part of an application rollback; additive migrations, outbox rows and payment checkpoints stay. — _why:_ external email/payment effects and newer user data cannot be undone safely by a restore.
- **OPS-064** `MUST NOT` Down-convert, reset or delete users' new-format data to make an old client boot. — _why:_ an older binary cannot understand or safely recreate new pending work.
- **OPS-065** `SHOULD` Trigger a rollback when a health dependency is down or the public release identity is wrong; when any duplicate payment, notification or queue side effect appears; when any OPS-059 smoke check fails (login/refresh, the disposable write, upload/document generation, websocket); or when error rate or latency materially exceeds the recorded stable baseline.
- **OPS-066** `AVOID` The platform's automatic rollback, which can also restore historical variables. Redeploy the retained image by deployment ID and compare digests. Platform image retention is not a backup strategy: keep the compatible previous release running in standby.
- **OPS-067** `GOTCHA` When changing what the gateway health-probes (e.g. switching to a liveness route), first deploy and verify the route on both slots. Before rolling back to a release that lacks it, unset the probe variable first. — _why:_ otherwise the only upstream answers 404 to the health probe and the site goes down.

## Health, logging and housekeeping

- **OPS-068** `SHOULD` Split health checks: a strict `/health` (database, Redis and storage, each with a ~1.5 s timeout plus `AbortSignal`, 503 if any is down) as the deploy gate; `/health/live` with no I/O for the gateway; `/health/ready` returning 503 only when the database is down, otherwise 200 `degraded`. The public body is only `{status}`; details (slot, mode, release SHA, checks) are token-gated per SEC-076 (`<HEALTH_TOKEN_HEADER>`, compared with `timingSafeEqual` on SHA-256 digests). — _why:_ a hanging dependency must not hold the probe open, and a Redis or storage outage must not take the site out of rotation.
- **OPS-069** `MUST` Add error tracking, uptime alerting (OPS-103), a `LOG_LEVEL` setting and a health endpoint whose successful probes stay out of access logs (SEC-056). Provide test-error triggers for server and browser, admin-only and rate-limited (SEC-020); after setup, check that a test event reaches the error tracker within a minute.
- **OPS-103** `SHOULD` Monitor uptime from outside: probe the readiness route (`/health/ready`, OPS-068) every 1-5 minutes from the production region, and alert on any non-200 or on `degraded` lasting more than 5 minutes. The owner creates the monitor and picks the alert recipient (owner-only action, PO-050).
- **OPS-070** `SHOULD` Log with pino, including `responseTime` and the error kind and code (e.g. Prisma error codes). Read logs per application slot, because the gateway only logs proxy lines. Log queries slower than `<SLOW_QUERY_MS>` (e.g. 300 ms) at WARN with model, action and duration, through a Prisma middleware registered first, so it is the outermost layer and times the whole chain; never log the query args, which can contain emails, addresses and tokens.
- **OPS-071** `MUST` After a Redis flush, move or data loss, confirm that no work was lost: the scheduler heartbeat re-created the repeatable jobs (STK-037; it does no domain work itself), the outbox replayed incomplete events, and the reconciliation sweep re-armed deadline jobs from database timestamps (design: ENG-046).
- **OPS-072** `MUST` Schedule cleanup of expired tokens, idempotency keys, orphan uploads and stale anonymous drafts.

## Production data operations

- **OPS-073** `MUST` Run production data operations only when the user explicitly asks. Ship each one-off correction as a committed script exposed through a named package script, with dry-run and confirm steps, and run it through the platform's run command against the database service. Update the seed script in the same change so fresh environments match. Never run ad-hoc SQL without a backup.
- **OPS-074** `MUST` Keep database credentials out of the agent's context: run `<PLATFORM_CLI> run --service <DB_SERVICE> -- powershell -File <script.ps1>`, where the script sets `$env:DATABASE_URL = $env:DATABASE_PUBLIC_URL`, or the bash form `<PLATFORM_CLI> run --service <DB_SERVICE> -- bash -c 'DATABASE_URL="$DATABASE_PUBLIC_URL" pnpm -F <backend> <script>'`. The switch to the public URL happens inside the child process because of OPS-075. Verify the result with read-only queries. — _why:_ credentials stay in the child process and never enter the agent's context, transcript or shell history.
- **OPS-075** `GOTCHA` `<PLATFORM_CLI> run` executes the command on your machine with the service's variables injected, so it cannot reach private-network hosts (e.g. `*.railway.internal`), including the injected private `DATABASE_URL`. Point tools started that way at the service's public URL, or at a temporary public domain.
- **OPS-076** `MUST` Destructive data scripts default to dry-run, require an explicit confirm env var (e.g. `<SCRIPT>_CONFIRM=yes`), print the target database host, and are preceded by a backup. Keep any real data the owner wants to retain.
- **OPS-077** `MUST NOT` Run demo/sample seeds against production (guard and env passwords: SEC-074).
- **OPS-078** `MUST` Before launch, remove demo data from production with a dedicated cleanup script run under OPS-076 (dry-run, confirm, backup first), and create the real admin with the seed-admin script (SEC-015, SEC-075).

## Backups and restore

- **OPS-079** `MUST` Run a scheduled off-site backup job as its own cron service. It writes a manifest (database version, applied migrations, critical triggers, per-table row counts) and a `pg_dump --format=custom` from the same exported snapshot (`pg_export_snapshot()` + `pg_dump --snapshot=...`), verifies the TOC, encrypts with age using only the PUBLIC key (the job refuses to start if the private key is present), deletes the plaintext, uploads dump + `.sha256` + manifest, and re-reads the upload to compare the hash. — _why:_ with the manifest and dump on different snapshots, the restore test reported false failures.
- **OPS-080** `MUST` Mirror object storage off-site with `rclone sync --backup-dir`, so deleted or overwritten objects are kept for 30 days.
- **OPS-081** `MUST` Apply backup retention only after a successful backup and never below a minimum number of daily copies (7). Email on failure with the failing step and redacted last log lines; stay silent on success apart from an optional dead-man-switch heartbeat.
- **OPS-082** `MUST` Run the monthly restore test as a separate service; only it holds the decryption identity. It picks the newest daily backup and checks its SHA-256 and age (older than `<MAX_BACKUP_AGE>`, e.g. 36 h, fails), decrypts (the identity sits on disk only while the decryptor runs), restores with a timed `pg_restore --exit-on-error` into a temporary database, compares applied migrations, critical triggers and per-table row counts with the manifest (volatile tables are informational), checks the storage mirror, deletes the decrypted files, and emails an OK/FAILED report with only counts and table names (no personal data) plus a heartbeat. Keep the "restore rehearsed" checklist item unchecked until a real report arrives. The `pg_restore` duration is the measured part of the RTO (OPS-084). Build the backup image in CI and run its retention test there (CI verifies it and does not publish it).
- **OPS-083** `MUST` Restore manually only into a NEW database, never over live production. Verify it against the manifest, point the inactive slot at it in standby and run the release checks before switching, re-apply deletions and anonymizations made after the backup date (from the audit trail), and delete the decrypted dump and key file afterwards.
- **OPS-084** `SHOULD` State RPO (derived from the backup schedule) and RTO (target set by the product owner, measured from restore-test durations plus the manual steps) explicitly in `<DEPLOYMENT_DOC>`.
- **OPS-085** `GOTCHA` `pg_restore` across PostgreSQL major versions only works upward: provision the target at a version greater than or equal to the source. Production may run a newer major than dev and CI, so SQL features available only in production will not be caught by tests.
- **OPS-086** `GOTCHA` Railway cron schedules run in UTC. Cron/backup services use `restartPolicyType: NEVER` and no health check, each with its own config-as-code file.
- **OPS-087** `MUST` When moving the production database or storage, verify the target against the source before reopening full traffic: migration count, per-table row counts, critical triggers, storage object counts and a hash sample, then the public-URL checks. Once the new database takes writes, rollback means a reverse migration. Repoint the backup services in the same window and run backup and restore-test immediately. Never leave any slot pointed at the old database. Keep the old data services traffic-free as a cold backup for 7-14 days, and ask the owner to delete them (OPS-008) only after a successful off-site backup and restore test from the new set. — _why:_ two "production" databases are a source of data loss.

## Region and latency

- **OPS-088** `MUST` Keep every service of a production stack (app slots, gateway, database, cache, object storage, backup jobs) in the same region (`<PROD_REGION>`). When requests are slow, first measure per-query latency and RTT for each service; code mitigations are temporary, the real fix is co-location. Move stateless slots one at a time (standby first, promote, then the other), and after any move verify that the fastest GET in the app logs drops from cross-region latency (~150 ms) to under ~20 ms. — _why:_ a cross-region database added ~150 ms per query and pushed interactive transactions past their timeout, causing 500s.

Code-side mitigations: ENG-012, STK-032.

## Email and domain

- **OPS-091** `MUST` Never launch with the dev mail sink (Mailpit) as the email transport; configure the transport only through `SMTP_*` env vars. Before launch, set up a real SMTP provider with SPF/DKIM/DMARC, test register → real inbox → verify → login end to end, then have the owner delete the publicly reachable mail-catcher service and its domain (owner action, OPS-008), because its inbox holds real password-reset links. — _why:_ a mail sink in production was a top-severity audit finding.
- **OPS-092** `SHOULD` For a real sending domain, start DMARC at `p=none` and move to `quarantine` after 2-4 clean weeks, use a monitored support mailbox as Reply-To instead of no-reply, and confirm SPF/DKIM/DMARC PASS on a test email. Every email also gets a plain-text variant and a `List-Unsubscribe` header (opt-out rules: SEC-117).
- **OPS-093** `GOTCHA` Moving to a new domain logs users out once (host-only cookies), needs 301 redirects from legacy hosts to the canonical host (defaulting to a reserved `.invalid` matcher when unset), a rebuild of every slot for baked public URLs, and a new payment webhook endpoint whose new signing secret must be set on both slots.

## Platform and CLI gotchas (Railway, Windows, Claude Code)

- **OPS-094** `GOTCHA` Railway injects its own `PORT` (e.g. 8080), so a public domain targeting a different port returns 502; set `PORT` explicitly on the service.
- **OPS-095** `GOTCHA` A deploy that fails with no logs can mean the image is no longer pullable (e.g. vendor images moved to a legacy repository); switch to a maintained official image (OPS-011). Services with mounted volumes may need `RAILWAY_RUN_UID=0`.
- **OPS-096** `GOTCHA` After a service is redeployed, private-network DNS takes about a minute to propagate; transient connection timeouts (e.g. SMTP) in that window heal on their own and are not a bug to chase.
- **OPS-097** `GOTCHA` On Railway's private network, every place that creates a Redis client (ioredis, BullMQ connections) needs the Redis password plus `family: 0`. — _why:_ IPv6 private networking needs dual-stack DNS lookups.
- **OPS-098** `GOTCHA` The Railway CLI links one directory at a time. Run `railway up` from PowerShell, with no path argument, only from the dedicated release worktree (OPS-101) and only after `railway link -p <project> -e <env> -s <service>` in that directory. From Git Bash inside a worktree it fails with "prefix not found"; from an unlinked directory it silently creates a new stray project; from a directory linked to another service it deploys there, so never let the app image land on the gateway service. `railway status` keeps showing the old deployment as Online while the new one builds, so poll `railway deployment list` and watch the deployment ID change.
- **OPS-099** `SHOULD` Deploy with `railway up --service <APP_SERVICE> --detach`, or `--ci` to stream the build.
- **OPS-100** `GOTCHA` The Claude Code auto-mode permission classifier refuses commands that would print credentials (`<PLATFORM_CLI> variables` without `--set`, `status --json`, `ssh`) and any deletion, and it can ask for fresh consent before a deploy even right after an approved one. A refusal is final: report it to the user and ask. Never rephrase, split or re-issue the command to get past it.

## Adapting to a new project

- Pick the platform and fill in `<PLATFORM_CLI>`, `<DEPLOY_CLI>`, `<APP_SERVICE>`, `<DB_SERVICE>`, `<PROD_REGION>`, and the slot and gateway service names; translate the Railway-specific gotchas (OPS-094 to OPS-099) to your platform's equivalents, or drop them.
- Decide the topology: start single-slot with migrate-on-boot (OPS-039), and plan the move to blue/green (OPS-044 to OPS-067) before real users write data. Budget for the two extra services.
- Name the deployment env vars (`DEPLOYMENT_MODE`, `RUN_MIGRATIONS`, `ACTIVE_UPSTREAM`, `RELEASE_SHA`, `LISTEN_HOST`, `LOG_LEVEL`) and the error codes `<STANDBY_ERROR_CODE>`, `<STALE_CLIENT_ERROR_CODE>` and `<NOT_CONFIGURED_CODE>`; encode their production rules in the boot-time config schema.
- Set `<RELEASE_TAG_PATTERN>`, write the CI deploy-gate script (OPS-031) and the slot-verification tool (OPS-052), and add the "Prod steps (after approval)" template to the sprint delivery protocol.
- Fill `<DEPLOYMENT_DOC>` (the kit installs a skeleton at `docs/08-deployment.md`): the dated current-state banner (OPS-102), promotion and rollback runbooks, the smoke checklist (OPS-059), rollback triggers, and RPO/RTO agreed with the product owner.
- Stand up the backup and restore-test services (OPS-079 to OPS-083) and the off-site bucket before launch, set `<MAX_BACKUP_AGE>` for the restore test, and choose who holds the age private key.
- Set `<SLOW_QUERY_MS>` for slow-query logging (OPS-070), and have the owner create the uptime monitor (OPS-103).
- Add the consent rules (OPS-001 to OPS-008, OPS-101) to `CLAUDE.md` and to every subagent prompt template, keep deploy and push commands off the permission allowlist, and keep the everyday working directory unlinked from production services.
