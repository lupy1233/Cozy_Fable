### 3.1 Concurrency on capacity-limited operations

Operations that consume a limited shared capacity (slots, stock, seats) run in a SERIALIZABLE transaction that locks the parent row with `SELECT ... FOR UPDATE`, with an explicit transaction timeout (`<CAPACITY_TX_TIMEOUT>`, e.g. 10 s; never raised to absorb latency). Authoritative steps:

- Lock the parent row (`FOR UPDATE` via a raw query).
- Check that the parent's status is in the allowed set and the parent is not soft-deleted; otherwise return the "not allowed" code.
- Count the active children; if the count has reached the cap, return the "capacity full" code.
- Check the actor: eligibility, balance, per-actor limits, exclusions.
- Insert the child together with its ledger and side records.
- Update the parent's aggregate status.

Every operation that changes the number of active children under a capacity-limited parent (release, cancel, withdraw, reassign, background jobs) uses the same lock pattern, through one reference implementation.

- Transactions open only through one helper with named profiles (read / write / critical / capacity) that fix isolation, `maxWait`, timeout and retry; direct `$transaction` calls are banned by lint except in the helper, specs and seeds (ENG-003).
- Serialization failures (Prisma `P2034`, or `P2010` with SQLSTATE `40001`/`40P01`) are retried up to 3 times with a random 20–80 ms pause, then answered with a retryable 409, never 500 (ENG-004).
- A retrying callback has no effects outside the transaction: queue adds, HTTP calls, emails and socket emits run after commit (ENG-005).
- With no parent row to lock, serialize with `pg_advisory_xact_lock(hashtextextended('<type>:<id>', 0))` before counting (ENG-007).
- "At most one open X per parent" is re-checked under the lock AND backed by a partial unique index (ENG-008).

### 3.2 Idempotency of critical POSTs

Header `Idempotency-Key` (UUID v4 generated by the frontend) on every critical POST: capacity consumption, accept/commit actions, money-bearing creates, irreversible actions, payment webhooks, purchases. Receipt table `idempotency_receipts` (key, user_id, endpoint = method + concrete path, request_hash = sha256 of the canonical `{ body, query, userId }`, response_body, response_status, expires_at), dedup 24 h.

- Same key + endpoint + hash → replay the original status and body. Same key with a different hash or user → 409.
- Definitive 4xx answers are cached; a 5xx or unknown outcome is never stored as final (ENG-016).
- The receipt is reserved before execution and locked `FOR UPDATE` as the first statement of the domain transaction; an in-progress receipt never expires and is never re-executed automatically (ENG-017).
- The frontend sends critical mutations through an idempotent runner: one key per intent, kept across retries, memory only, button disabled while pending (ENG-018).

### 3.3 Timezone and business calendar

All datetimes are stored in PostgreSQL as `TIMESTAMPTZ` in UTC. Business-day and business-hour arithmetic happens only in one `BusinessCalendarService` configured with `<BUSINESS_TZ>` (IANA zone). Working days = weekends + fixed holidays from a library + a DB holidays table (movable holidays and admin overrides, seeded for `<YEARS>`).

- Every deadline is materialized into a `<x>_deadline_at` column when the triggering event happens; recalculations (pause, extension) update the column through a worker. Deadlines are never derived on read (ENG-038).
- Settings changes apply only to new calculations; materialized deadlines are not recomputed.
- **Clock rule:** short operational timers (minutes up to a couple of days: grace periods, warnings, assignment windows) are WALL-CLOCK hours. Only business deadlines count working days. Each timer is classified in the timers table of `03-business-rules.md` (ENG-037).
- The UI formats business dates with a formatter pinned to `<BUSINESS_TZ>`, never the browser's `toLocaleString` (ENG-040).
- GOTCHA: `Intl.DateTimeFormat#formatToParts` has no milliseconds; truncate to the second and refine the conversion twice on DST days (ENG-039).

### 3.4 File storage

`StorageService` exposes `getPresignedUploadUrl` / `getPresignedDownloadUrl` / `deleteObject`. Mandatory flow:

- `POST /uploads/presign` (filename, mimeType, size, entityType, entityId) → backend validates MIME allowlist, size and target entity → row in `stored_files` with status `AWAITING_UPLOAD` → presigned PUT (~15 min) with Content-Type and Content-Length bound into the signature.
- The frontend PUTs directly to MinIO/S3.
- `POST /uploads/:id/complete` → backend HEADs the object, compares size and MIME, copies it to a sealed server-only key → `AWAITING_SCAN` → enqueue scan.
- Scan worker → `CLEAN` or `QUARANTINED` (a mock in the MVP; say so plainly, SEC-083).
- Reads: presigned GET (~5 min), issued only after an inline authorization check, and only for `CLEAN` files.

Files are NEVER reachable through a static URL and NEVER served through an application endpoint. Limits: `<MAX_UPLOAD_BYTES>` per file, `<MAX_FILES_PER_ENTITY>` per entity, counted under a per-entity advisory lock. Archives are untrusted and get no preview.

### 3.5 Realtime and domain events

Socket auth is cookie-based (the same httpOnly cookie). At handshake, middleware validates the access token; when it has expired, the server sends an auth-expired event and the client refreshes, then reconnects. Events are emitted ONLY through `EventBusService.publish(event, payload, targetUserIds, eventId)`, which emits on Socket.IO and enqueues the notification job; controllers, services and jobs never emit directly. Redis adapter mandatory from Sprint 1.

- Durable outbox: the intent row is written in the same transaction as the domain change, keyed by a deterministic event key (`<event>:<entityId>:<reason-or-deadlineMs>`); the dispatcher is the only caller of `publish`, leases batches, caps attempts and dead-letters poison rows (ENG-050..052).
- A private event carries non-empty target user IDs; without targets it is a no-op, never a broadcast (ENG-053).
- Payloads carry IDs and status metadata only — never emails, names, message text, signed URLs or credentials (ENG-054).
- Delivery is at-least-once; frontend handlers are idempotent; a failed post-commit enqueue never turns a committed action into a 500 (ENG-055, ENG-056).

### 3.6 Frontend state boundaries

- TanStack Query: all API data (single source of truth).
- Zustand: pure UI state only (modals, sidebar, local pre-submit drafts, UI filters, theme). NEVER API data.
- React Hook Form: only the state of the form being filled in.
- Optimistic updates through TanStack `onMutate`/`onError`, never through Zustand; for quickly toggled sets, roll back with the inverse operation on the affected item (ENG-125).
- Socket handlers only invalidate query families; they never hold or write data (ENG-126).
- If server state ever seems to need duplicating into Zustand, stop and ask.
- Sprint 0 deliverable: `STATE_CONVENTIONS.md` with 5 worked examples.

### 3.7 Payments and webhooks

Path A (admin UI): `POST /admin/payments/:id/confirm`. Path B (provider webhook): `POST /webhooks/payment`, signature verified over the raw body (HMAC-SHA256 with a secret from env, or the provider SDK) + replay protection. Both call one `PaymentsService.confirm(paymentId, source)`, with `source` recorded in the audit log (ENG-023).

- The webhook dedupes on the provider event ID in `processed_webhook_events`, answers 200 quickly, returns 500 on a processing error so the provider retries, and marks the event processed only after success (ENG-021).
- Confirmation checks amount, currency and owner, and grants benefits only through a conditional pending → paid transition (ENG-022).
- Before calling the provider, persist a checkpoint with an opaque attempt key reused on every retry (ENG-020).
- Mock payments and placeholder legal identity values never reach production (SEC-049).

### 3.8 Rate-limited external lookups

*Delete if the product calls no rate-limited third-party lookup (geocoder, enrichment API, ...).*

`<PROVIDER>` is called at write time through a dedicated BullMQ queue throttled to the provider's limit (`<RATE>`); derived values are stored on the record. Cache table keyed by the normalized query (including every parameter), TTL `<CACHE_TTL>`. Search in tiers from most to least specific; fail only when every tier fails. Filtering on derived values (e.g. distance) happens in SQL. Seeds never call the provider (ENG-118, QA-081).

### 3.9 Audit log

NestJS interceptor + `@Audit('domain.action')` decorator; the interceptor awaits the insert before responding. Captures user ID, role, IP (hashed with a salt from env), user agent, entity type, entity ID, timestamp. Before/after snapshots ONLY from an explicit allowlist of non-sensitive fields. NEVER passwords, tokens, message content, free text or PII. Append-only enforced in the DB by a `BEFORE UPDATE OR DELETE` trigger on the audit table that raises an exception (ENG-088, ENG-089).

- Audit is written only after success; a spec checks both the decorator metadata and the interceptor wiring of every critical route (SEC-051, SEC-052).

### 3.10 Errors and response format

Single format: `{ error: { code, message, details, timestamp, traceId } }`, produced by one global exception filter. Codes are UPPER_SNAKE_CASE constants in `<SHARED_PKG>`, documented in `ERROR_CODES.md`. The frontend maps codes to localized messages (<LOCALES>); it uses `message` only as a fallback.

- A 500 never carries a raw message, a stack or ORM/provider text (ENG-090).
- Transient DB errors (`P2028`, `P2024`, `P1001`, `P1017`) → 503 with a retryable "busy" code and `Retry-After: 2`; nothing was saved (ENG-006).
- `details` is structured and translatable (`[{ field, messageKey }]`), never free text or PII (ENG-093).

### 3.11 Minimal observability

Structured JSON logging with a `traceId` per request. Health checks: strict `/api/v1/health` (DB, Redis, storage, each with a ~1.5 s timeout; 503 if any is down) as the deploy gate, `/health/live` with no I/O, `/health/ready` (OPS-068). Failed BullMQ jobs are visible in an admin jobs view. Error tracking, uptime alerting and a `LOG_LEVEL` setting (OPS-069). Telemetry failures are swallowed and never break a user flow (ENG-120).

### 3.12 Soft delete and data protection

Entities holding PII have a nullable `deleted_at TIMESTAMPTZ` (and `anonymized_at` where relevant). A Prisma extension adds `deleted_at IS NULL` to top-level reads of an explicit model list; relations, includes and raw SQL filter explicitly. A bypass exists only as a server-side `AsyncLocalStorage` helper taking a reason from a closed union (ENG-076). `UserAnonymizationService.anonymizeUser(userId)` replaces email, name and phone with hashes and sets `anonymized_at`; the audit log keeps only the user ID.

- GET handlers never write (ENG-079).
- GOTCHA: `PrismaPromise` is lazy — await it inside the `AsyncLocalStorage` context (ENG-077).

### 3.13 Auth, sessions, 2FA

- Tokens live only in httpOnly cookies (Secure in production, SameSite=Lax), never in localStorage/sessionStorage (SEC-004).
- Refresh token rotation on every refresh, with a ~30 s grace window for multi-tab races; reuse after the grace window revokes the whole token family (theft detection) (SEC-005). The access token is bound to its session family (SEC-006).
- Session policy: `<SESSION_POLICY>` (default: one active session per user — a new login on another device revokes the previous family and sends auth-expired to the old socket, SEC-011).
- 2FA (TOTP): `<2FA_POLICY>` (default: built into schema, routes and UI, inactive behind a feature flag; the guard is a no-op while the flag is off, ENG-112).
- Passwords: bcrypt cost 12, never in logs, audit or responses (SEC-012). Secrets in env, validated at boot by a Zod config schema — boot fails fast when one is missing (SEC-064).
- Rate limiting in tiers (SEC-020): credential routes ~5/min, session refresh ~30/min, capacity- or money-moving operations ~10/min, uploads ~30/min, global 100/min per IP; counters in Redis (SEC-021). Per-account sign-in lockout (SEC-024).
- Strict CORS allowlist with credentials, Helmet, CSP with a per-request nonce in production (SEC-090..093).

### 3.14 State machines and settlement

- Every "happens once" transition is a conditional update on the expected source status (`updateMany({ where: { id, status: { in: allowedFrom } } })`); `count === 0` means someone else handled it → no-op or 409 (ENG-025).
- Settlement ticket: only the path whose conditional update returned `count === 1` may move money or balances or emit events (ENG-026). All settlement goes through one service function, enforced by lint (ENG-027).
- Coupled state machines are one system: forced transitions on the coupled machines happen in the same transaction (ENG-029).
- Every non-terminal state has a visible exit (timeout, auto-transition, admin action); no dead ends (ENG-030).
- Irreversible or paid actions go through a confirmation dialog with server-provided consequences and nothing preselected (ENG-032, SEC-048).

### 3.15 Time-based jobs and reconciliation

- Every waiting state has a timed exit: a BullMQ delayed job enqueued after commit, with a deterministic `jobId` built from the entity ID and the deadline timestamp; a moved deadline gets a new jobId (ENG-042).
- Handlers are idempotent: they re-read DB state, exit early on a stale job, and apply changes with a conditional update + deterministic outbox key (ENG-043).
- Redis is never the only holder of deadlines: a reconciliation sweep (hourly and at boot) re-arms due or missing jobs from the deadline columns (ENG-046).
- Jobs never write another domain's tables directly and never emit realtime messages (ENG-045).

### 3.16 Money and computed values

*Delete if the product handles no money or internal balances.*

- Money is stored as integer minor units or `NUMERIC`/`Decimal(12,2)`, never FLOAT (ENG-063).
- Every derived value (totals, tax, scores) is computed on the server from raw inputs, rounded half-up; the client never sends derived values (ENG-064). The value shown and the value charged come from the same function (ENG-066).
- Values that depend on settings at event time are snapshotted and never updated (ENG-067).
- Fiscal documents are numbered SERIES-NUMBER, gap-free, allocated under per-series serialization at READ COMMITTED (ENG-068, ENG-069); an issued document is never deleted (ENG-071).
- Financial tables use foreign keys with `onDelete: Restrict`; balances have `CHECK (>= 0)`; the ledger is the source of truth (ENG-072).

### 3.17 Versioned definitions and persisted formats

- Published versions of definitions that stored data depends on (form flows, content schemas) are frozen; a breaking change goes into a new version file (ENG-096).
- Stable field IDs never change when screens are reordered (ENG-097).
- JSON columns are persisted formats: new fields are optional and additive; any other change needs a backward reader + test (ENG-098).
- Client-persisted formats are versioned; unknown or future versions are rejected, never overwritten (ENG-102).

### 3.18 Shared domain logic and validation

- Cross-app types, Zod schemas, constants, the error-code registry and pure domain computation live in `<SHARED_PKG>` (ENG-104).
- Each domain constraint is enforced in three layers: normalizer, shared schema at the API boundary, UI that hides impossible options (ENG-105). The server re-applies UI-locked invariants on create and edit (ENG-107).
- Use `??`, not `||`, wherever 0 is a valid value (ENG-109).

### 3.19 Tunable parameters and feature flags

- Tunable business parameters (durations, thresholds, limits, fiscal data) live in the `app_settings` key/value table, read through a typed `SettingsService` with one exported defaults constant; admin changes are validated and audited; new keys are added by migration with `ON CONFLICT DO NOTHING` (ENG-110).
- Role permissions are a frozen role → permissions matrix in `<SHARED_PKG>`; plan entitlements are data (ENG-111).
- Features planned for later are built in fully and kept inactive behind a flag (ENG-112). Optional integrations default to disabled when unconfigured; a missing browser capability falls back to a working UI (ENG-116, ENG-117).
